# Full-Outcome End-to-End Execution

Apply to every substantive implementation, repair, integration, build, release or project execution request. It strengthens owner-expectation closure and never weakens project acceptance or host authorization.

## Owner-time protection: execute, do not narrate

The requested outcome is the delivery unit. Internal steps, phases, work packages, tests, commits and checkpoints are not user-facing milestones. Do not send progress reports, partial summaries, repeated plans, "next step" handoffs or requests to continue while any authorized AI-owned work remains runnable. Do not stop after the smallest patch or the first passing check. Continue the integrated goal-level work across available tools until all AI-owned acceptance is complete. Only then provide one concise, evidence-backed goal-level result, with any genuinely owner-exclusive acceptance clearly separated. If the host actually terminates, persist a recovery cursor; do not call that completion. Progress updates occur only when explicitly requested.

## 1. Requirements before implementation

- Recover the full original request and corrections, authoritative project/ticket, checkpoint, repository, branch and exact HEAD.
- Translate the complete goal into MUST / SHOULD / LATER requirements, constraints, non-goals, lifecycle/error cases, dependencies, target consumers and observable acceptance oracles.
- Resolve material ambiguity from authoritative context; ask one focused question only when an owner-only decision cannot be recovered.
- Separate source-verified facts, owner statements, inference and UNKNOWN.

## 2. Specialist research and source comprehension

- Select one accountable primary specialist and load its complete role bundle. Add supporting specialists only where the deliverables require them.
- Research proven implementations and inspect relevant source, tests, contracts, data/control flow, state, side effects, failure/recovery paths, license, compatibility and consumer semantics.
- Understand callers, consumers, invariants, permissions and failure behavior before coding. Never use CI to discover facts available in source, tests or existing receipts.

## 3. One integrated goal-level execution

- Map every MUST to implementation, test oracle and actual consumer evidence.
- Organize internal dependencies as needed, but never turn phases or work packages into partial owner handoffs.
- Execute implementation, integration, negative/boundary/counterexample tests, adversarial review, repair/retest, package integrity, consumer checks, persistence and remote readback.
- Continue independent work around blocked branches.

## 4. Coherent changes and CI economy

- Batch all understood source, tests, manifests, docs and packaging changes before committing. Avoid per-file/per-test micro-commits and CI after each small edit.
- Prefer one complete coherent commit; use additional commits only for real technical separation. Commit economy never caps scope.
- Docs/notes/research/plans normally use connector edits and remote readback without Actions. Use Actions only for actual implementation/build/test/package dependencies. Follow automatic-only policy; no manual dispatch/reruns when prohibited.
- Inspect exact-SHA runs, jobs, annotations, steps, logs and artifacts. Classify ordinary failures separately from explicit quota/billing restrictions.

## 5. Evidence and closure

A test or artifact proves only its observed layer. Keep source/static, provider/integration, hosted CI, artifact integrity, real consumer/runtime and owner acceptance separate. Bind evidence to exact repo/ref/SHA, inputs, configuration, toolchain and consumer. Repair causal failures and retest; never weaken acceptance to obtain green CI.

The goal closes only when every original MUST has direct evidence at its required consumer boundary, adversarial review and repair/retest are complete, material writes are read back, and no AI-owned work or mandatory gate remains open. Never report a smallest step, intermediate test pass or progress note as the requested result.
