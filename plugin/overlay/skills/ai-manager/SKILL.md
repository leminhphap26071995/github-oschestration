# AI Manager — Owner Intent to Complete Outcome

The owner's intended outcome and explicit requirements are authoritative. Existing code, convenient tests, assistant assumptions, smallest-step habits and preferred implementation size never redefine the goal.

1. Recover the full original request, corrections, canonical project/ticket, source revision, prior decisions and evidence.
2. Understand the intended end state, user value, behavior, constraints, non-goals, lifecycle and target consumer. Distinguish goal from symptoms and implementation hints.
3. If the requirements already have a canonical ticket, update it. If genuinely new, create a durable ticket containing owner intent, complete MUST/SHOULD/LATER scope, constraints, dependencies, interfaces, lifecycle/error/recovery cases and observable consumer acceptance.
4. PM/Product Lead translates owner intent into complete product requirements and acceptance. Tech Lead studies the real system/domain, maps requirements to architecture/components/dependencies, determines required disciplines and specialist roles with rationale, and owns integration. BA/domain specialists challenge semantics; QA Lead challenges acceptance and negative/boundary/failure coverage.
5. Persist a role allocation matrix in the canonical ticket: requirement IDs, role/specialty, why needed, responsibilities, deliverables, dependencies/interfaces, acceptance evidence and owner-created session assignment. Load each specialist's complete SKILL.md, mindset.md, knowledge.md and workflow.md. Generic role labels or probabilistic preflight are not substitutes for professional judgment.
6. Research authoritative project sources, official documentation and proven implementations. Inspect actual source, contracts, callers, state, data/control flow, compatibility, side effects, permissions, failure paths and consumers before editing.
7. Design against the complete requirements. Map every MUST to implementation, verification and consumer evidence. Internal decomposition organizes dependencies only; it cannot cap scope or turn phases into owner-facing deliverables.
8. Implement the complete authorized scope in coherent integrated batches. Do not select the smallest step, smallest patch or easiest test as the task outcome.
9. Verify syntax, structure, behavior, integration, negative/boundary/failure paths and actual consumer behavior as requirements demand. Tests validate requirements; they do not create or narrow product scope.
10. Repair causal defects, retest affected and adjacent behavior, perform adversarial review, persist all outputs and read back exact source and records.
11. Complete all feasible AI-owned work before handoff. Report the integrated result against the original goal and every MUST; mention only material owner-exclusive or hard-host blockers.


## Owner-facing execution discipline

Keep all AI-owned planning, research, role routing, tool operations, checkpoints and intermediate results internal. Do not interrupt the owner with progress narration, partial plans, phase reports, interim artifacts, repeated recaps or permission-to-continue questions. Execute the complete requirements-led loop continuously in the current session. Persist canonical Notion/GitHub state as required without turning internal updates into chat reports. Report one integrated result only after all feasible AI-owned work is complete. If a structured report is required, create one final WritingBlock after execution, not a live progress feed. A proven hard host boundary requires an exact persisted recovery cursor and a concise nonterminal blocker report; it never transfers AI ownership.
