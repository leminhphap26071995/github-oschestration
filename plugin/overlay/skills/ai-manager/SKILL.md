# AI Manager — Requirements, research and complete delivery

The owner's intended outcome is authoritative. Existing code, convenient tests, patch boundaries and assistant assumptions never redefine it.

## Goal anchor and context integrity — before every material iteration
Load `skills/goal-anchored-context-integrity/SKILL.md`. Lock the original user expectation, immutable MUST criteria, scope/non-goals, project/ticket identity, source authority, exact repo/ref/SHA, evidence provenance, open gates and one Next Action. Re-read the original request and canonical source after context breaks, corrections and failures. Never fill missing context with plausible details.

1. **Recover source first:** Resolve live project/router, original goal, requirements, exact repo/ref/HEAD, latest checkpoint/plan, recent implementation, current failure and evidence. For GitHub tasks use connected GitHub/Notion reads first; no local ChatGPT preflight may block them. Project `AGENTS.md` and its deterministic gate are authoritative for that project; invoke the gate when required.
2. **Understand requirements before design:** Record/version MUST/SHOULD/LATER, constraints, non-goals, target consumers, lifecycle/error cases, dependencies and observable E2E acceptance oracles. Challenge ambiguity, contradictions, omitted paths, assumptions, security/privacy, feasibility and testability. Validate against authoritative sources. Do not code from a symptom or guessed interpretation.
3. **Research before coding:** Inspect internal solutions and proven public/open-source implementations, products, libraries and standards. Read relevant source, tests, docs, API contracts, maintenance/release state, license, compatibility and runtime limitations. Reverse-engineer the mechanism: trace data/control flow, state transitions, callers/callees, invariants, side effects, failure/recovery paths and test strategy. Compare reuse, adaptation and replacement; assess REA/RAG/retrieval only when a demonstrated requirement benefits. Record selected method and why alternatives do not fit. Research is complete when the implementation approach and its failure behavior are understood—not when a token number of links has been collected.
4. **Design once against full scope:** Map each MUST to implementation components, tests, consumer evidence and dependencies. Resolve architecture before editing. Do not discover requirements by coding. Keep the architecture only if evidence shows it satisfies the complete requirement set.
5. **Understand source before editing (gate 5):** Inspect affected modules and call sites. Know inputs/outputs, contracts, invariants, state, side effects, concurrency, permissions, errors and downstream consumers at the exact SHA. If a construct is not understood, inspect/research first. Every meaningful change must have a requirement or evidenced defect rationale.
6. **Coherent batching (gate 6), not a scope cap:** Implement the complete authorized scope and its requirement-derived tests together. Do not patch one file, trigger CI, patch another file and repeat. Prefer one or two coherent commits for a normal task; commit count is an efficiency preference, never an acceptance boundary or reason to stop. Continue further coherent batches when real dependencies or runtime limits require them. No micro-commits, per-file commits or commit-per-test.
7. **Verify each batch (gate 7):** Run appropriate checks after a coherent batch. Derive test oracles from requirements and authoritative product behavior; never weaken an oracle merely to make CI green. Inspect all failures and artifacts, identify causal defects, repair and retest until affected acceptance criteria pass or a genuine external/owner-only gate remains. Separate static/unit/contract/integration/provider/browser-runtime/artifact/owner gates.
8. **Failure-triggered goal revalidation:** After the first failed attempt, re-read the original goal and all MUST criteria before retry. Before a second attempt or after a second failure of the same method, run a full goal revalidation and change the method/test/evidence route. Every retry must add new evidence or a discriminating test; no repeated hypothesis/action without information gain. Maintain one active falsifiable hypothesis per failure branch.
9. **Follow CI to terminal evidence:** For GitHub, inspect automatic workflow triggers and observe the exact-SHA run through queue, runner, every job and step, completion, logs and artifacts. A partial pass or in-progress run is not a final verdict. Do not manually dispatch/rerun under automatic-only policy. Continue monitoring during the active execution; if the observation window ends, persist the exact cursor and resume rather than claiming completion.
10. **Finish:** Perform consumer/E2E checks, adversarial review, repair/retest, artifact inspection, remote readback and checkpoint. Do all feasible AI-owned work. Owner testing is reserved for genuinely owner-exclusive access/observation; record it as OWNER_PENDING without shifting routine QA to the user.
11. **Report at goal level:** Compare every original MUST to direct evidence. Preserve exact repo/ref/SHA and evidence provenance. Mark PASS/FAIL/UNKNOWN/BLOCKED/OWNER_PENDING. Do not report the smallest step or latest fix as the requested outcome. A plan, patch, unit test, green CI or release is not product acceptance. Never claim E2E completion with open gates.
