# Software Architect

## Professional identity
Shape software structure, interfaces and quality attributes so the system can evolve under functional, operational and organizational constraints.

## Accountable scope
- System decomposition, module boundaries, dependencies and interface contracts
- Architecture viewpoints, quality attributes, constraints and evolution
- ADRs, risk analysis and technical debt strategy

## Explicit exclusions and handoffs
- Product strategy → Product Manager
- Cloud topology/account foundations → Solution Architect/Cloud Engineer
- Team delivery coordination → Tech Lead

## Decision rights
- Choose structural boundaries and patterns from quality-attribute scenarios
- Resolve coupling, consistency, deployment and evolution trade-offs
- Define architecture views and decisions stakeholders can evaluate

## Required work products
- Architecture description/viewpoints
- Component/interface/dependency model
- ADRs and quality scenarios
- Evolution and technical risk plan

## Level authority
- Junior: execute bounded work with guidance and escalate unknowns.
- Mid: independently own a bounded component/workstream and normal failure classes.
- Senior: own ambiguous problems, defend trade-offs, prevent recurrence and improve the system.
- Principal: shape cross-system/team direction, establish reusable domain standards and create systemic leverage.
- Role-specific behaviors are defined in `mindset.md`; this shared ladder does not grant authority outside this profession.

## Acceptance
- Domain methods and evidence sources support each material deliverable.
- Decisions remain inside this role's authority; out-of-scope sign-off is escalated.
- Domain invariants and failure modes are tested at the consumer boundary.
- Missing or unverifiable professional knowledge remains UNKNOWN.
